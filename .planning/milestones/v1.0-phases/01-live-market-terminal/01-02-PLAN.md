<objective>
Make the watchlist editable end to end and make the price feed survive a failing data provider.

**User story (MVP):** **As a** trader watching live prices, **I want to** add and remove tickers from my watchlist and trust that prices keep flowing even when the real market-data provider fails, **so that** the terminal stays useful and honest instead of going quiet or silently lying about where its numbers come from.

Purpose: Two halves of one concern — the active ticker set stays correct under user change (add/remove) and under provider failure (permanent failover). Both mutate what the running market-data source tracks, and both must keep the `watchlist` table, the `PriceCache`, and the SSE stream in agreement.

Output: `backend/app/watchlist/` (router with GET/POST/DELETE), watchlist mutation queries in `backend/app/db/connection.py`, `backend/app/market/failover.py` (`FailoverMarketDataSource`), a permanent-failure guard in `backend/app/market/massive_client.py`, the inline add/remove UI, and new tests for all of it.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `POST /api/watchlist` | Untrusted ticker string crosses into SQL parameters and into the market-data source |
| browser -> `DELETE /api/watchlist/{ticker}` | Untrusted path segment crosses into SQL parameters |
| Massive API -> backend | Untrusted third-party response payloads and exception messages cross into the cache and the log |
| process env -> `MassiveDataSource` | `MASSIVE_API_KEY` crosses into an SDK client and into exception paths |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-08 | Tampering | `add_watchlist_ticker`, `remove_watchlist_ticker`, `ticker_has_open_position` | high | mitigate | All three bind `ticker` and `user_id` through `?` placeholders; SQL text is a literal string in source. `AddTickerRequest` additionally constrains the normalized ticker to `A-Z`, `.` and `-` before it reaches the query. |
| T-01-09 | Information Disclosure | watchlist 409 / 404 error bodies | medium | mitigate | `HTTPException` with a short fixed `detail` string; no stack traces, no SQL text, no echo of raw input beyond the normalized ticker. Asserted by `tests/watchlist/test_router.py`. |
| T-01-10 | Tampering | untrusted `snap.ticker` / `snap.last_trade` from the Massive response | medium | mitigate | The existing narrow `except (AttributeError, TypeError)` per-snapshot handler in `_poll_once()` is preserved unchanged; malformed provider payloads are skipped with a warning rather than poisoning the cache. |
| T-01-11 | Information Disclosure | Massive exception messages and failover log lines | high | mitigate | The failure handler logs the exception type and message via lazy `%s` formatting and never formats `self._api_key`, the `RESTClient`, or `os.environ` into a record. A `caplog` test raises an exception embedding a fake key and asserts no emitted record contains it. |
| T-01-12 | Repudiation | silent switch from real to simulated prices | high | mitigate | Failover emits an `error`-level log line naming the transferred ticker count, sets a durable `failed_over` flag, and `GET /api/health` reports the currently active `market_source` — so the transition is observable after the fact rather than invisible. |
| T-01-13 | Denial of Service | repeated failed Massive polls burning the rate limit | medium | mitigate | This plan is the mitigation: `_poll_loop()` exits on permanent failure, so a bad key or an outage produces exactly one failed call rather than one every 15 seconds for the process lifetime. |
| T-01-02 | Denial of Service | unbounded watchlist growth via repeated `POST /api/watchlist` | low | accept | Carried forward from Plan 01-01. No cap is specified in `planning/PLAN.md`; single-user local app, no network exposure. |
| T-01-05 | Spoofing | unauthenticated watchlist mutation | low | accept | Carried forward from Plan 01-01: no auth anywhere by explicit product decision (`planning/PLAN.md` section 2, `.planning/REQUIREMENTS.md` Out of Scope). |
