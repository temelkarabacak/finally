<objective>
Make money real in FinAlly: a user can buy and sell shares from the terminal and watch cash, positions, and total portfolio value change instantly.

**User story (MVP):** **As a** trader with $10,000 of simulated cash, **I want to** buy and sell shares instantly from the terminal, **so that** I can build a position and watch my cash and portfolio value move with the market.

Purpose: This is the phase's tracer slice — the thinnest path that touches every layer the phase will modify (trade bar → REST endpoint → price cache → SQLite transaction → portfolio read → header). Everything else in Phase 2 is a visualization built on top of the `/api/portfolio` contract this plan establishes, so the response shape and the trade transaction are a contract, not an implementation detail. Phase 3's LLM copilot executes trades through this exact same `execute_trade` function.

Output: `backend/app/portfolio/` (valuation, trades, snapshots, router), the router mounted in `main.py`, `frontend/hooks/usePortfolio.ts`, `frontend/components/TradeBar.tsx`, an extended header, and a passing end-to-end trade test.
</objective>

**A. `backend/app/portfolio/valuation.py` — one valuation, three call sites.** Module docstring, `from
__future__ import annotations`, module logger. Define `POSITION_EPSILON = 1e-9` and
`QUANTITY_PRECISION = 8`. Import `DEFAULT_USER_ID` from `app.db` and `PriceCache` from `app.market`.

`position_views(conn, cache, user_id=DEFAULT_USER_ID) -> list[dict]` selects `ticker, quantity, avg_cost`
from `positions` where `user_id = ?` and `quantity > ?` (pass `POSITION_EPSILON`, not literal 0 — a
residual quantity left by float drift after a full sell must not surface as a dust row), ordered by
`ticker`. For each row: `current_price = cache.get_price(ticker)`; when it is `None` fall back to
`avg_cost` for valuation and emit `current_price: None` in the dict so the client can tell the
difference. Compute `market_value = quantity * effective_price`,
`unrealized_pnl = (effective_price - avg_cost) * quantity`, and
`unrealized_pnl_percent = 0.0 if avg_cost == 0 else (effective_price - avg_cost) / avg_cost * 100`.
Round every monetary field to 2 places and `quantity` to `QUANTITY_PRECISION`. A position whose ticker
has no cached price therefore shows P&L of exactly 0.00 and 0.00% — never blank, never `NaN`.

`compute_total_value(conn, cache, user_id=DEFAULT_USER_ID) -> float` reads `cash_balance` from
`users_profile` and adds the sum of `market_value` across `position_views`, returning the result rounded
to 2 places.

`portfolio_view(conn, cache, user_id=DEFAULT_USER_ID) -> dict` assembles the `GET /api/portfolio` body
in the interface contract above, deriving `holdings_value` and `unrealized_pnl` from the same
`position_views` list it returns so the three numbers can never disagree with each other. This one
function is the only place portfolio arithmetic lives — the trade response and the snapshot recorder
both call it rather than repeating the formula.

**B. `backend/app/portfolio/snapshots.py` — the write half only.**
`record_snapshot(conn, total_value, user_id=DEFAULT_USER_ID, recorded_at=None) -> None` inserts one row
into `portfolio_snapshots` with `uuid.uuid4().hex` as `id` and `recorded_at or
datetime.now(UTC).isoformat()`. It is a bare `conn.execute` with no transaction control of its own,
because Plan 02-01 calls it from *inside* an already-open trade transaction and Plan 02-03 will call it
from a background loop. Document that constraint in the docstring. The 30-second loop and the history
query arrive in Plan 02-03 — do not build them here.

**C. `backend/app/portfolio/trades.py` — the transactional core.** This is the most load-bearing file
in the phase; follow 02-RESEARCH.md's "Explicit-Transaction Trade Execution Skeleton" closely.

`class TradeError(Exception)` carries `.detail` (the human-readable message the API returns) and `.code`
(a short machine tag: `no_price`, `insufficient_cash`, `insufficient_shares`).

`new_position_after_buy(old_qty, old_avg_cost, buy_qty, price) -> tuple[float, float]` returns
`(old_qty + buy_qty, (old_qty * old_avg_cost + buy_qty * price) / (old_qty + buy_qty))`. Write it with
no zero-quantity branch: when `old_qty` is 0 the first term vanishes and the result is exactly `price`,
which is the correct basis for a freshly reopened position. Adding a special case here would be dead
code that can drift from the general one.

`execute_trade(conn, cache, ticker, side, quantity, user_id=DEFAULT_USER_ID) -> dict`:

  1. `ticker = normalize_ticker(ticker)`.
  2. `price = cache.get_price(ticker)`; if `None`, raise `TradeError` with code `no_price` and the
     UI-SPEC message "No live price for {ticker} yet — add it to your watchlist first." A market order
     has no price to fill at, and inventing one would make "instant fill at current price" untrue.
  3. Read the current position (`SELECT quantity, avg_cost FROM positions WHERE user_id = ? AND
     ticker = ?`), defaulting to `(0.0, 0.0)` when absent, and `cash_balance` from `users_profile`.
  4. Branch on side. **Buy:** `cost = quantity * price`; if `cost > cash + POSITION_EPSILON` raise
     `TradeError` code `insufficient_cash` with the UI-SPEC message "Not enough cash to buy {quantity}
     {ticker} — try a smaller quantity." Otherwise compute the new quantity and average cost via
     `new_position_after_buy` and `new_cash = cash - cost`. **Sell:** if
     `quantity > old_qty + POSITION_EPSILON` raise `TradeError` code `insufficient_shares` with the
     UI-SPEC message "You only hold {held} shares of {ticker} — try a smaller quantity." Otherwise
     `new_qty = old_qty - quantity`, `new_avg_cost = old_avg_cost` (a sale does not change the basis of
     the shares still held), and `new_cash = cash + quantity * price`. When `new_qty` lands at or below
     `POSITION_EPSILON`, store it as exactly `0.0` so float drift cannot leave a dust position alive in
     `get_active_tickers()` forever.
     Every rejection happens here, **before any write** — the request is refused in full, and the
     requested quantity is never reduced to whatever the balance or holding could afford.
  5. Round `new_qty` and `new_avg_cost` to `QUANTITY_PRECISION` and `new_cash` to 2 places.
  6. Open the transaction with `conn.execute("BEGIN")`. Inside a `try`: UPSERT `positions` with
     `INSERT INTO positions (...) VALUES (...) ON CONFLICT(user_id, ticker) DO UPDATE SET
     quantity=excluded.quantity, avg_cost=excluded.avg_cost, updated_at=excluded.updated_at`; INSERT the
     `trades` row; `UPDATE users_profile SET cash_balance = ? WHERE id = ?`; then call
     `record_snapshot(conn, compute_total_value(conn, cache, user_id), user_id, now_iso)` so the P&L
     chart gains a point immediately after every trade (PORT-04's post-trade trigger); finish with
     `conn.execute("COMMIT")`. On any exception `conn.execute("ROLLBACK")` and re-raise.
     This explicit SQL transaction is mandatory and not decorative: the shared connection is opened with
     `autocommit=True` (`backend/app/db/connection.py` line 51), under which `Connection.commit()` and
     `Connection.rollback()` are documented no-ops and each `execute()` commits on its own. Without the
     explicit block, a failure between the position write and the cash write leaves the user holding
     shares they never paid for.
  7. Keep every SQLite call in this function synchronous and direct — no thread-pool offload, no
     coroutine awaited between `BEGIN` and `COMMIT`. On a single-threaded event loop a coroutine only
     yields at an await point, so a block with no await inside it is what serializes this trade against
     a concurrent trade request and against Plan 02-03's periodic snapshot writer. Introducing an await
     mid-transaction would reopen exactly the interleaving window the transaction exists to close, so no
     `asyncio.Lock` is needed or wanted.
  8. Return the response dict from the interface contract, sourcing `total_value` and the `position`
     entry from `portfolio_view`/`position_views` so the trade response and a follow-up
     `GET /api/portfolio` agree exactly.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /api/portfolio/trade` | Untrusted ticker, side, and quantity cross into money-mutating code |
| trade handler → SQLite | Four writes must land as one unit or not at all |
| PriceCache → fill price | The only source of the price a market order fills at |
| API response → React render | Server-supplied strings and numbers become DOM content |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | `TradeRequest` fields reaching SQL | high | mitigate | Every query in `trades.py`, `valuation.py`, `snapshots.py`, and `router.py` uses `?` placeholders with a parameter tuple; no query string is built by concatenation or f-string. `ticker` additionally passes `normalize_ticker` plus `_TICKER_PATTERN` (`^[A-Z.\-]+$`), so no separator character survives validation. |
| T-02-02 | Tampering | partially-applied trade under `autocommit=True` | high | mitigate | `execute_trade` wraps its four writes in explicit `BEGIN` / `COMMIT` with `ROLLBACK` on any exception, because `Connection.commit()` is a documented no-op in this connection mode. Task 2's rollback test proves it against a forced mid-transaction failure. |
| T-02-03 | Tampering | double-spend from two concurrent trade requests reading stale cash | high | mitigate | No await occurs between `BEGIN` and `COMMIT` and every SQLite call is synchronous, so on the single-threaded event loop a second request's `SELECT cash_balance` cannot run until the first transaction has committed. Task 2 covers the sequential-buy case. |
| T-02-04 | Tampering | quantity clamped rather than refused, letting an over-budget order partially fill | high | mitigate | Both sufficiency checks raise `TradeError` before the transaction opens; the requested quantity is used verbatim or the request is refused in full. Task 2 asserts zero side effects after every refusal. |
| T-02-05 | Tampering | float drift admitting a sell larger than the holding, or leaving an immortal dust position | medium | mitigate | Sufficiency comparisons carry `POSITION_EPSILON = 1e-9`; `quantity` and `avg_cost` are rounded to 8 places on write; a residual quantity at or below the epsilon is stored as exactly `0.0`, and `position_views` filters on `quantity > POSITION_EPSILON`. |
| T-02-06 | Information Disclosure | error responses leaking database internals or file paths | low | mitigate | Only curated `TradeError.detail` strings reach the client via `HTTPException(400, detail=...)`; unexpected exceptions propagate as FastAPI's generic 500 with no body detail. |
| T-02-07 | Repudiation | trade history mutated or overwritten | low | accept | The `trades` table is written by a single append-only `INSERT` with a fresh UUID per row and is never updated or deleted anywhere in this plan; a single-user simulated portfolio needs no stronger audit control at ASVS L1. |
| T-02-08 | Tampering | rendering server-supplied `detail` and ticker strings into the DOM | medium | mitigate | Every value renders as a JSX text child, which React escapes; `dangerouslySetInnerHTML` appears nowhere in the frontend. |
| T-02-SC | Tampering | package-manager installs | n/a | accept | This plan adds no npm or Python package. `recharts` is the phase's only new dependency and is gated behind the blocking legitimacy checkpoint in `02-04-PLAN.md`. |
</threat_model>
