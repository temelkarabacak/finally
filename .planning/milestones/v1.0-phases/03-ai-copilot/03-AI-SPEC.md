## 1. System Classification

**System Type:** Conversational — single-turn, non-streaming structured-output assistant with server-side auto-execution (not RAG, not Multi-Agent, not Autonomous Agent — no retrieval, no tool-calling loop, no agent handoff)

**Description:**
FinAlly's chat panel lets the sole (single-user, `user_id="default"`) trader converse with an AI assistant — "FinAlly, an AI trading assistant" — that is grounded in their live cash, positions/P&L, and watchlist prices on every turn. The assistant replies with a structured JSON response (`message`, optional `trades[]`, optional `watchlist_changes[]`); the backend auto-executes any trades/watchlist changes it names through the exact same validation as manual actions (no confirmation dialog, by design — simulated money, zero stakes) and reports success or rejection back inline. "Good" means: every action the assistant claims to have taken actually happened (or was rejected and truthfully reported as such), the assistant never fabricates portfolio state it wasn't given, and a slow or broken LLM call fails safely (no trade, generic retry message, nothing corrupted in `chat_messages`).

**Critical Failure Modes:**
<!-- The 3-5 behaviors that absolutely cannot go wrong in this system -->
1. The assistant's reply claims a trade or watchlist action succeeded when it was actually rejected or never executed (silently-dropped or misreported action) — user believes they hold a position they don't.
2. A malformed or partial structured-output response (bad JSON, missing required field) crashes the request instead of degrading to a safe generic-error reply — this is exactly what TEST-02 exists to prevent.
3. A trade or watchlist action executes with a hallucinated ticker or a quantity the model invented rather than one the user actually asked for.
4. The 30-second timeout path executes a trade anyway, or leaves a corrupted/partial row in `chat_messages` (violates CHAT-05's "no trade executed, failed attempt not persisted").
5. The assistant's portfolio commentary is grounded in stale or fabricated numbers instead of the live cash/positions/prices actually passed into the prompt — user makes a decision on numbers that were never real.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Consumer fintech / trading-terminal UX — specifically a simulated-money retail trading copilot, not a regulated brokerage or investment-advisory product. (This is a capstone-course educational build: fake $10,000 starting balance, no real securities, no real order routing, single hardcoded `user_id="default"`, no login.)

**User Population:** A single, sole local user of the demo/course app — the person running the FinAlly container on their own machine. There is no multi-user, no real customer base, and no one else's money or data is ever at stake.

**Stakes Level:** Low. No real currency moves, no real trades reach any market or broker, and no real financial harm is possible from a bad trade decision. The stakes that *do* exist are entirely about product trust and correctness, not financial or regulatory risk: does the UI honestly reflect what the backend actually did, and does the assistant stay grounded in the numbers it was actually given.

**Output Consequence:** When the assistant's structured response includes `trades[]`/`watchlist_changes[]`, the backend auto-executes those actions immediately with no confirmation step, and the results (success or rejection) are shown inline in the chat as fact. Because there's no confirmation dialog, the chat transcript *is* the only place the user learns what happened to their (simulated) portfolio — if the transcript misreports it, the user has no other way to notice except by cross-checking the positions table/portfolio view themselves.

### What Domain Experts Evaluate Against

Even though this is a zero-stakes simulated system, the right practitioner reference point is how retail trading-copilot and tool-using-agent products are judged in production — where the standard is "does the transcript match what actually happened," not "is the trading advice good." Research on agentic financial tool-use consistently identifies **action-report fidelity** and **evidence-grounding** as the load-bearing dimensions once auto-execution and no-confirmation UX are involved.

```
Dimension: Action-report fidelity (did-it-really-happen honesty)
Good: Every trade/watchlist action the assistant's chat message narrates matches exactly what the executed_trades/executed_changes list actually contains (ticker, side, quantity, success/rejection) — no action is claimed that wasn't executed, no executed action goes unmentioned.
Bad: The chat message says "Bought 10 shares of AAPL" when the trade was actually rejected for insufficient cash, or omits mentioning a rejection entirely, leaving the user to believe they hold a position they don't.
Stakes: Critical
Source: Agentic tool-use research identifies "deception" — an agent telling the user it performed an action when it actually didn't, or vice versa — as a named, recurring failure mode in tool-calling financial agents (FinTrace, arXiv 2604.10015).
```

```
Dimension: Context grounding (no fabricated portfolio numbers)
Good: Every cash figure, position, P&L number, or price the assistant states in its commentary is traceable to the live portfolio_context object built fresh for that turn — nothing is invented, extrapolated, or carried over from a stale prior turn.
Bad: The assistant states a cash balance, position size, or price that doesn't match what was actually in the prompt for that turn (fabricated or stale).
Stakes: Critical
Source: Evidence-conditioned faithfulness research on financial LLM agents — a response can look grounded but be unreliable if not actually conditioned on the data it was given (FinToolBench, arXiv 2603.08262).
```

```
Dimension: Structured-output schema compliance (degrade safely, never crash or half-execute)
Good: A malformed/non-JSON or schema-invalid model response is caught, logged at warning level, and produces the generic retry message with zero trades executed and zero rows persisted — the same outcome as a timeout.
Bad: A malformed response causes an unhandled exception, a partially-executed trade list, or a corrupted/partial `chat_messages` row.
Stakes: Critical
Source: Documented, reproducible behavior of `gpt-oss-120b` ignoring `response_format` and returning free-form text (litellm#16014, Groq community reports) — this is the exact scenario TEST-02 exists to cover.
```

```
Dimension: Action scope discipline (no invented tickers/quantities)
Good: Every ticker and quantity in an executed trade/watchlist change traces back to something the user actually said or clearly implied in their message — the assistant doesn't invent a ticker never mentioned or round/pad a quantity the user didn't ask for.
Bad: The assistant executes a trade for a ticker or quantity the user never referenced, or "helpfully" resizes a requested quantity without being asked.
Stakes: High
Source: Practitioner tool-calling guidance — invocations must be traceable to explicit user intent; unrequested scope expansion in an auto-executing (no-confirmation) system is the highest-leverage way for an agent to cause an unwanted state change (Giskard, "Function calling in LLMs: Testing agent tool usage for AI Security").
```

```
Dimension: Honest failure/timeout messaging
Good: On a 30s timeout or malformed-output path, the user sees a plainly generic "something went wrong, try again" message — never a message that implies analysis happened or a trade was considered.
Bad: The retry message is worded in a way that suggests the assistant "looked at" the portfolio or "decided" something before failing, when in fact nothing was evaluated.
Stakes: Medium
Source: Conversational-AI trust design guidance — silent or misleadingly-worded failures erode trust faster than an honest, obviously-generic error state (Built In, "How to Design Conversational AI Interfaces Users Actually Trust").
```

### Known Failure Modes in This Domain

1. **"Deception" via mismatched narration and execution** — the single most-cited failure mode in tool-calling financial agent research: the natural-language reply and the actual tool/execution result diverge, and because there's no confirmation dialog in this system, the chat message is the user's only signal. This is exactly Critical Failure Mode #1 in Section 1 above, and directly why CHAT-04/CHAT-05's persist-only-after-successful-execution ordering matters.
2. **Silent/plausible-looking failures that don't look like failures** — a response that returns HTTP 200, renders a normal-looking assistant bubble, and reads as coherent, but is quietly wrong (stale numbers, an unexecuted-but-narrated trade). Standard uptime/response-code monitoring cannot catch this class of failure; it requires evaluating the transcript against what the backend actually did, not just whether a response was returned.
3. **Numerical hallucination under structured-output pressure** — models under a hard JSON-schema constraint (especially smaller/faster inference paths like `gpt-oss-120b` on Cerebras, tuned here for low latency via `reasoning_effort="low"`) can produce internally-consistent-looking but fabricated numbers, or ignore `response_format` entirely and emit free text — a documented, model-specific issue for this exact model, not a generic LLM caveat.
4. **Scope creep on auto-executed actions** — because there is no confirmation step (by design, per PLAN.md), any tendency of the model to "round up," substitute a similar ticker, or add an unrequested watchlist change has an immediate, irreversible (within the simulated portfolio) effect, unlike a chat-only assistant where a wrong suggestion is merely read, not acted on.

### Regulatory / Compliance Context

None. This is a single-user, no-login, simulated-money educational/course capstone project — no real securities are bought or sold, no real order ever reaches a market or broker, and no real user funds are at risk. There is no real "customer," no investment advice with real-world financial consequence, and therefore no FINRA/SEC broker-dealer, RIA/investment-adviser, or suitability-rule obligations apply. This assessment should be revisited only if the project's scope ever changes to handle real money, real brokerage connectivity, or multiple real users — none of which are in scope per PLAN.md or REQUIREMENTS.md.

## 2. Framework Decision

**Selected Framework:** Direct LiteLLM `completion()` call — no agent orchestration framework

**Version:** `litellm>=1.98.0`, `pydantic>=2.13.0`

**Rationale:**
Phase 3 is one non-streaming LLM call per user message that returns a fixed JSON schema, which the backend then executes server-side against the existing portfolio/watchlist code paths. There is no retrieval, no tool-calling loop, no multi-agent handoff, and no state machine to checkpoint — every candidate framework in the decision matrix would add an abstraction layer over a single `completion()` call. The call pattern itself (model, provider routing, structured output) is already fixed by `planning/PLAN.md` §9 and `.claude/skills/cerebras/SKILL.md`, so this is confirmation, not an open decision. LiteLLM alone supplies the only cross-cutting service a framework would otherwise offer here: provider routing to Cerebras via OpenRouter and a uniform structured-output interface.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangChain / LangGraph / CrewAI / LlamaIndex / OpenAI Agents SDK / Claude Agent SDK / AutoGen / Google ADK / Haystack | Eliminated pre-scoring by hard constraints: PLAN.md §9 fixes the exact call signature; no multi-agent, agentic-planning, or retrieval requirement exists. Matrix anti-pattern #1 applies directly ("Using LangChain for simple chatbots — direct SDK call is less code, faster, easier to debug"). |
| Raw OpenAI-compatible `httpx` POST to OpenRouter (schema enforced via prompt + Pydantic validation on the response) | Only needed as a fallback if `litellm`'s `response_format` proves unreliable against `gpt-oss-120b` on the Cerebras provider. Removes a dependency rather than adding an abstraction — consistent with "do not overengineer," but not needed unless the primary pattern fails. |

**Vendor Lock-In Accepted:** Partial — the project is committed to OpenRouter + Cerebras + `openrouter/openai/gpt-oss-120b` per PLAN.md §9 (not an open decision), but LiteLLM keeps the call-site code itself provider-agnostic, so swapping providers later is a config change, not a rewrite.

### Core Imports
```python
import asyncio
import json
import logging

from litellm import completion
from openai import APITimeoutError  # litellm re-raises provider timeouts as this
from pydantic import BaseModel, Field, ValidationError
```

### Entry Point Pattern
```python
"""Minimal working shape for the Phase 3 chat call — one non-streaming,
structured-output completion per user turn, run off the event loop."""

MODEL = "openrouter/openai/gpt-oss-120b"
EXTRA_BODY = {"provider": {"order": ["cerebras"]}}
MAX_TOKENS = 1024  # explicit bound — see 4b.3, never leave unbounded
TIMEOUT_S = 30

logger = logging.getLogger(__name__)


class TradeAction(BaseModel):
    ticker: str
    side: str  # "buy" | "sell"
    quantity: float


class WatchlistChange(BaseModel):
    ticker: str
    action: str  # "add" | "remove"


class ChatResponse(BaseModel):
    message: str
    trades: list[TradeAction] = Field(default_factory=list)
    watchlist_changes: list[WatchlistChange] = Field(default_factory=list)


def _call_llm_sync(messages: list[dict]) -> str:
    """Blocking call — must only ever run inside asyncio.to_thread()."""
    response = completion(
        model=MODEL,
        messages=messages,
        response_format=ChatResponse,
        reasoning_effort="low",
        extra_body=EXTRA_BODY,
        max_tokens=MAX_TOKENS,
        timeout=TIMEOUT_S,
    )
    return response.choices[0].message.content


async def get_chat_response(messages: list[dict]) -> ChatResponse | None:
    """Returns None on timeout/malformed output — caller shows the generic
    retry message and does not persist a failed assistant turn (CHAT-05)."""
    try:
        # asyncio.to_thread mirrors the established idiom in
        # app/market/massive_client.py._poll_once() for wrapping a
        # synchronous SDK call without blocking the event loop.
        raw = await asyncio.to_thread(_call_llm_sync, messages)
        return ChatResponse.model_validate_json(raw)
    except APITimeoutError:
        logger.warning("LLM call timed out after %ss", TIMEOUT_S)
        return None
    except (ValidationError, json.JSONDecodeError) as e:
        # gpt-oss-120b occasionally ignores response_format and returns
        # free-form text instead of JSON — treat identically to a timeout.
        logger.warning("LLM returned malformed structured output: %s", e)
        return None
```

### Key Abstractions
| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `completion()` | LiteLLM's single synchronous entry point for any provider, OpenAI-compatible signature | Every chat turn — one call per user message |
| `response_format=<PydanticModel>` | Tells LiteLLM to request structured JSON matching the model's schema and to attach it as raw JSON text on `.choices[0].message.content` | Whenever the reply must be machine-parsed (this system, every turn) |
| `extra_body` | Pass-through dict merged into the raw provider request body | Provider routing (`{"provider": {"order": ["cerebras"]}}`) — fixed by the cerebras skill, not optional |
| `reasoning_effort` | Controls gpt-oss's internal reasoning budget before emitting the final answer | Set to `"low"` per the skill — keeps latency inside the 30s budget |
| `asyncio.to_thread()` | Stdlib bridge that runs a blocking call in the default thread pool without blocking the event loop | Wrapping every `completion()` call, since LiteLLM's `completion()` is synchronous |

### Common Pitfalls
1. **`response_format` can get silently stripped or rewritten for OpenRouter models.** LiteLLM's OpenRouter adapter has a documented history of not recognizing OpenRouter as schema-capable and dropping/rewriting the JSON schema before it reaches the provider ([litellm#11652](https://github.com/BerriAI/litellm/discussions/11652)). The skill-mandated call (`response_format=ChatResponse` directly, not nested in `extra_body`) is the fixed pattern to use — but verify empirically in this exact `litellm>=1.98.0` version that the schema survives to the wire (e.g. log `response._hidden_params` or inspect the request) before trusting it in production.
2. **`gpt-oss-120b` has a documented tendency to ignore `response_format` and return free-form text instead of JSON**, reported across Groq, Bedrock, and LM Studio deployments ([litellm#16014](https://github.com/BerriAI/litellm/issues/16014), [Groq community](https://community.groq.com/t/structured-outputs-ignored-by-openai-gpt-oss-120b/687)). This is exactly the failure TEST-02 exists to catch — `model_validate_json()` must be wrapped in `try/except (ValidationError, json.JSONDecodeError)` and degrade to the generic retry message, never crash the request.
3. **`completion()` is synchronous** — calling it directly inside an `async def` FastAPI route blocks the single event loop for the entire LLM round-trip (up to 30s), stalling every other request including the SSE price stream. Always wrap it in `asyncio.to_thread()`, matching the pattern already established for the Massive REST client.
4. **`timeout=30` tears down the actual HTTP connection**, raising `openai.APITimeoutError` (LiteLLM re-maps provider/SDK timeouts to the `openai.*` exception hierarchy — see `litellm.exception_mapping`). Do not additionally wrap the call in `asyncio.wait_for(..., timeout=30)`: a double timeout risks the outer one firing first and leaving the thread-pool call still running in the background with no handle to cancel it.
5. **`max_tokens` is absent from the cerebras skill's example snippets.** Left unset, a verbose or looping generation can both blow past a reasonable cost/latency budget and increase the odds of a truncated (thus JSON-invalid) response. Set it explicitly (e.g. `max_tokens=1024`) — see 4b.3.

## 4. Implementation Guidance

**Model Configuration:**
`openrouter/openai/gpt-oss-120b` via LiteLLM, routed to Cerebras with `extra_body={"provider": {"order": ["cerebras"]}}` (fixed by PLAN.md §9 / the cerebras skill). `reasoning_effort="low"` to keep latency inside the 30s budget. `response_format=ChatResponse` (the Pydantic model, passed directly — not JSON-schema-dict form, per skill). `timeout=30` passed to `completion()` directly. `max_tokens=1024` set explicitly (not in the skill's example, added here per 4b.3 — production calls must never leave `max_tokens` unbounded). No `temperature` override — leave provider default; this is a deterministic-schema task, not a creative one, and the skill doesn't specify one.

**Core Pattern:**
```python
async def handle_chat_message(conn, user_text: str, mock: bool) -> ChatResponse | None:
    """One /api/chat turn. Returns None on timeout/malformed output — caller
    persists nothing further and returns the generic retry message."""
    # 1. Persist the user's message BEFORE calling the LLM (CHAT-04) so it
    #    survives a subsequent timeout/error.
    save_chat_message(conn, role="user", content=user_text, actions=None)

    # 2. Build fresh context every turn — live portfolio/prices are NOT
    #    stored in chat_messages, only conversational turns are.
    portfolio_ctx = build_portfolio_context(conn, price_cache)  # cash, positions+P&L, watchlist
    history = load_recent_chat_messages(conn, limit=20)
    messages = build_messages(SYSTEM_PROMPT, portfolio_ctx, history, user_text)

    # 3. Call the LLM (mock branch bypasses the network call entirely).
    if mock:
        parsed = mock_chat_response(user_text)          # app/llm/mock.py, D-11
    else:
        parsed = await get_chat_response(messages)        # None on timeout/malformed JSON

    if parsed is None:
        return None  # router returns the generic retry message; nothing else persisted

    # 4. Auto-execute actions through the EXISTING validated code paths —
    #    same validation as manual trades/watchlist edits, no duplication.
    executed_trades = [execute_trade(conn, t) for t in parsed.trades]
    executed_changes = [apply_watchlist_change(conn, c) for c in parsed.watchlist_changes]

    # 5. Persist the assistant turn + actions only after successful
    #    generation and execution (CHAT-04/05).
    save_chat_message(
        conn, role="assistant", content=parsed.message,
        actions=json.dumps({"trades": executed_trades, "watchlist_changes": executed_changes}),
    )
    return parsed
```

**Tool Use:**
No LLM-native tool-calling API is used — `system_type` is Conversational with server-side auto-execution, not an agentic tool loop. The model's only "tool" is its structured `trades[]`/`watchlist_changes[]` output; the backend interprets that list and calls directly into the existing `app/portfolio` and `app/watchlist` functions (the same functions manual trade/watchlist endpoints call), so trade/quantity validation (insufficient cash/shares) is never duplicated or re-implemented for the LLM path.

**State Management:**
Conversation state lives entirely in the `chat_messages` SQLite table (already in the schema, per CONTEXT.md). Write ordering follows the explicit-transaction discipline established in Phase 2's trade execution: the user message write happens in its own commit before the (awaited) LLM call; the assistant message + `actions` JSON write happens in a second transaction after the LLM call and any trade/watchlist execution complete — no `await` (the LLM call) ever happens inside an open `BEGIN`/`COMMIT` block. Nothing is held in server memory across requests; every turn reloads the last 20 messages plus a freshly computed portfolio snapshot from the DB/price cache.

**Context Window Strategy:**
Fixed-window truncation, not summarization: only the most recent 20 `chat_messages` rows are sent (CHAT-02/PLAN §9), and live portfolio/price context is rebuilt fresh every turn rather than accumulated in history. `gpt-oss-120b` has a 131,072-token context window (per OpenRouter), so 20 short conversational turns plus a compact JSON portfolio snapshot is a small fraction of the budget — no reranking, chunking, or summarization pass is needed at this scale. Revisit only if message count/size assumptions change materially.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs with Pydantic

The response contract is defined once in `app/llm/schemas.py` and reused for both the live call and mock mode, so both paths are guaranteed to produce the same shape the router expects:

```python
from pydantic import BaseModel, Field


class TradeAction(BaseModel):
    ticker: str
    side: str  # "buy" | "sell"
    quantity: float


class WatchlistChange(BaseModel):
    ticker: str
    action: str  # "add" | "remove"


class ChatResponse(BaseModel):
    message: str
    trades: list[TradeAction] = Field(default_factory=list)
    watchlist_changes: list[WatchlistChange] = Field(default_factory=list)
```

**How LiteLLM integrates it:** pass the class itself as `response_format=ChatResponse` to `completion()` (not a JSON-schema dict — the skill's mandated form). LiteLLM converts it to a provider-side JSON-schema constraint where supported, and the raw text is validated client-side with `ChatResponse.model_validate_json(response.choices[0].message.content)`.

**Retry logic:** given the hard 30-second budget and CHAT-05's requirement that a failed turn is never partially persisted, the default policy is **no automatic re-call** on a validation failure — a second attempt risks exceeding the timeout the frontend already promises the user (D-09/D-10 render the failure as a normal inline error and leave the input box populated for a manual one-click resend, which is the actual retry mechanism). On `ValidationError` or `json.JSONDecodeError`: log the exception plus a truncated (e.g. first 500 chars) copy of the raw response at `logger.warning()` — never at `.error()`/`.critical()`, this is an expected, handled condition, not a system fault — and return the same "generic retry message, no trade executed, turn not persisted" path used for timeouts. Do not log full raw responses containing portfolio data at `info` level routinely; the warning-level truncated log is for debugging malformed-output frequency only.

### Async-First Design

LiteLLM's `completion()` is a synchronous call (there is no `acompletion()` used here — the mandated skill pattern is the sync form). The one common mistake is calling it directly inside an `async def` route handler: since FastAPI/uvicorn run a single-threaded event loop and market data (`SimulatorDataSource`/SSE) and portfolio endpoints share that same loop, a blocking `completion()` call stalls every concurrent client — including the price stream — for up to 30 seconds. The fix, already established in this codebase for the synchronous Massive REST client (`app/market/massive_client.py`'s `asyncio.to_thread(self._fetch_snapshots)`), is to wrap every `completion()` call in `asyncio.to_thread()`.

**Stream vs. await:** this system deliberately awaits the complete response rather than streaming (PLAN.md §9, point 9 — "no token-by-token streaming, Cerebras is fast enough"). This is the correct choice here specifically *because* the output must be validated as complete, well-formed JSON before any trade can be auto-executed — a partial JSON stream can't be safely parsed or acted on mid-flight. Streaming is the right call for plain conversational text UX; awaiting is the right call whenever the response feeds a structured-output validation gate, as it does here.

### Prompt Engineering Discipline

**System vs. user separation:** a static `role="system"` message (FinAlly's identity/instructions — PLAN.md §9's "concise and data-driven" guidance) is sent once per call, unchanged across turns. The dynamic portfolio context (cash, positions+P&L, watchlist prices) is rebuilt fresh every turn and injected as its own message immediately before the new user turn — not folded into the system prompt (which should stay static and cacheable) and not stored as part of the persisted `chat_messages` history (only the conversational `role`/`content` is persisted; the live numbers must never be replayed stale from a prior turn).

**Few-shot:** inline in the system prompt, not dynamically retrieved — there's no retrieval infrastructure in this phase and the schema is small (3 fields, 2 short sub-lists), so 1-2 compact canonical examples embedded directly in the system prompt are enough to anchor the output shape without meaningfully growing the token budget per call.

**`max_tokens`:** the cerebras skill's example snippets omit it entirely — set it explicitly in production (e.g. `max_tokens=1024`, generous enough for a conversational reply plus a handful of trade/watchlist entries, tight enough to bound cost and reduce the chance that a runaway generation both costs more and gets truncated mid-JSON). Never ship a call without an explicit `max_tokens`.

### Context Window Management

Conversational, non-RAG system: the strategy is fixed-window truncation, not summarization. Only the last 20 `chat_messages` rows are replayed (CHAT-02), and the portfolio/price context is recomputed live each turn rather than accumulated — so context never grows unbounded across a long session the way an open-ended agent transcript would. At `gpt-oss-120b`'s 131,072-token context window, 20 short turns plus a compact JSON portfolio snapshot is negligible; a summarization pass is unnecessary at this scale and would add complexity (and its own hallucination surface) with no measurable benefit here. Reassess only if a future phase allows much longer histories or much larger per-turn payloads.

### Cost and Latency Budget

**Per-call cost:** `openai/gpt-oss-120b` on OpenRouter is priced at roughly $0.03/1M input tokens and $0.17/1M output tokens (OpenRouter pricing page). A typical turn — system prompt + few-shot + 20-message history + portfolio JSON (~1-2K input tokens) plus a `max_tokens=1024` reply — costs well under $0.001 per chat turn; for a single-user demo app this is immaterial, but the explicit `max_tokens` cap is still what keeps a worst-case turn bounded.

**Caching:** not implemented in this phase, and not warranted — each turn's prompt is unique (live portfolio numbers change every call), so exact-match caching would rarely hit, and semantic caching would risk serving stale portfolio state or a stale trade decision, which directly conflicts with the phase's "never fabricate/stale portfolio numbers" failure mode. Skip caching here by design, not by oversight.

**Sub-task model routing:** not applicable — there is exactly one call type (the full chat turn) with no separable cheap sub-tasks (no classification/routing/summarization step exists in this phase's scope) to route to a smaller model.

## 5. Evaluation Strategy

> **Scope note (read first).** This is a solo capstone build: one developer, one local user, simulated money, no production traffic, no ops team, no eval budget. The evaluation strategy below is therefore **pytest-first** — every Critical dimension is reduced to a deterministic code-based check that runs offline with `LLM_MOCK=true`, no API key, and no network. That is not a compromise: it is achievable *because* the highest-stakes failure modes here (misreported actions, malformed-output crashes, timeout side effects) are structural, not subjective. LLM-judge and hosted-tracing options are recorded as clearly-marked stretch goals and are **not** required for Phase 3 completion.

### Dimensions

Grounded directly in Section 1b's domain rubric ingredients and Section 1's Critical Failure Modes (CFM #1-5). Every Critical dimension is code-measurable.

| ID | Dimension | Rubric | Measurement | Priority |
|----|-----------|--------|-------------|----------|
| **EV-1** | **Action-report fidelity** (1b: did-it-really-happen honesty; CFM #1) | **PASS:** The `actions` payload returned to the client and persisted to `chat_messages.actions` is constructed *only* from the return values of `execute_trade()` / `apply_watchlist_change()` — every entry carries the real outcome (filled, or rejected with reason). A trade rejected for insufficient cash appears as a rejection in both the API response and the DB row. **FAIL:** The response echoes `parsed.trades` (what the model *asked for*) as if it were what happened; or a rejected trade is reported as filled; or an executed action is missing from the payload. | **Code** — pytest with a stubbed executor forced to reject; assert response `actions` and the persisted JSON both show `success=false` + reason, and that no code path echoes model-proposed actions. (Narrative prose consistency: Human spot-check, EV-1b below.) | **Critical** |
| **EV-2** | **Structured-output degradation safety** (1b: degrade safely, never crash or half-execute; CFM #2) | **PASS:** Free-form text, truncated JSON, valid JSON missing `message`, and wrong-typed `quantity` each return `None` from `get_chat_response()`, log at `warning`, yield HTTP 200 + the generic retry message, execute zero trades, and persist zero assistant rows. **FAIL:** Any of those inputs raises an unhandled exception, executes a partial trade list, or writes a partial `chat_messages` row. | **Code** — this is TEST-02 verbatim; parametrized malformed-payload fixtures against `ChatResponse.model_validate_json`. | **Critical** |
| **EV-3** | **Timeout safety / no partial persistence** (CFM #4; CHAT-05) | **PASS:** A simulated `APITimeoutError` produces the generic retry message, executes no trade, persists no assistant row, and leaves the user's message row (written pre-call per CHAT-04) intact and uncorrupted. **FAIL:** A trade executes on the timeout path, an assistant row is persisted, or the user row is rolled back/lost. | **Code** — monkeypatch the client to raise `APITimeoutError`; assert DB state row-by-row (1 user row, 0 assistant rows, 0 new trades). | **Critical** |
| **EV-4** | **Context grounding — input half** (1b: no fabricated portfolio numbers; CFM #5) | **PASS:** The messages array sent to the model contains the live cash, each open position with its P&L, and current watchlist prices read from the `PriceCache` *for that turn*; no portfolio figures are replayed from `chat_messages` history. **FAIL:** The prompt omits live context, or stale portfolio numbers leak in via persisted history. | **Code** — build `build_messages()` from a fixture cache with known sentinel values; assert every sentinel appears in the payload and that history rows contain only `role`/`content`. | **Critical** |
| **EV-4b** | **Context grounding — output half** (same 1b dimension, generation side) | **PASS:** Every cash/position/P&L/price figure the assistant *states in prose* matches the context object for that turn. **FAIL:** The reply states a balance or price that was never in the prompt. | **Human** — read ~5 real (non-mock) transcripts against the logged context before marking the phase done. *(LLM-judge automation: stretch, see below.)* | **High** |
| **EV-5** | **Action scope discipline** (1b: no invented tickers/quantities; CFM #3) | **PASS:** In mock mode, each D-11 pattern rule produces exactly the ticker and quantity implied by the input and nothing more — no extra ticker, no rounded/padded quantity, no unrequested watchlist change. Unknown/invalid tickers and non-positive quantities are rejected by the *existing* shared validation, not by LLM-path-specific code. **FAIL:** A turn executes an action whose ticker or quantity is absent from the input, or the LLM path re-implements (and thereby weakens) trade validation. | **Code** (mock mode, deterministic by D-11) + **Human** (live-mode scenario review) | **High** |
| **EV-6** | **Honest failure messaging** (1b: honest failure/timeout messaging) | **PASS:** Timeout and malformed-output paths both return one shared module-level constant string that is plainly generic and implies no analysis occurred. **FAIL:** Two divergent error strings, or wording like "I reviewed your portfolio but..." that implies work happened. | **Code** (assert identity against the single constant, both paths) + one **Human** read of the constant's wording | **Medium** |
| **EV-7** | **Chat API contract** (CHAT-01; TEST-03) | **PASS:** `POST /api/chat` returns 200 with `{message, actions}` on success; rejects empty/missing message with 422; response shape is identical across mock and live modes. **FAIL:** Shape drift between modes, or a 500 on any handled failure path. | **Code** — TEST-03 route tests via `httpx`/`TestClient`. | **High** |

**Why EV-1 is code-measurable at all:** the design decision that makes it so is *derive the reported actions from execution results, never from the model's claim*. If the router builds its `actions` payload out of `execute_trade()` return values, the domain's top-cited failure mode ("deception" — narrating an action that didn't happen) becomes structurally impossible for the machine-readable half of the response, and only the free-text prose remains judgment-dependent (EV-4b/EV-5 human checks). Planner: treat this as an implementation constraint, not just a test.

## 6. Guardrails

Deliberately few. Four of the five are already implied by the Section 4 core pattern — they are called out here so the planner treats them as non-negotiable invariants rather than incidental implementation details. None adds meaningful latency; three add none at all.

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| **Structured-output validation gate** — `ChatResponse.model_validate_json()` on the raw response | Non-JSON, schema-invalid, or truncated model output | **Block.** Return `None` before *any* execution; generic retry message; nothing persisted; `logger.warning()` with the exception plus first ~500 chars of raw output. Covers CFM #2. |
| **Hard 30s timeout** — `timeout=30` passed to `completion()` (single timeout only; no outer `asyncio.wait_for`, per Pitfall #4) | LLM round-trip exceeds budget | **Block.** Identical path to the validation gate: no trade, no assistant row, generic retry message. Covers CFM #4 / CHAT-05. |
| **Shared validation for LLM-proposed actions** — LLM actions call the *same* `execute_trade()` / `apply_watchlist_change()` as manual endpoints | Insufficient cash, insufficient shares, unknown/invalid ticker, non-positive quantity | **Reject that action** (never clamp, per PORT-03) and report the rejection inline via the failed-styled card (D-05). The LLM path gets zero privilege over the manual path; validation is never re-implemented for it. Covers CFM #3. |
| **Execution-derived action reporting** — the `actions` payload is built from executor return values, never from `parsed.trades` | Always on | **Structural.** Makes "claimed but not executed" unrepresentable in the machine-readable response. Covers CFM #1 — the domain's top-cited failure mode. |
| **Bounded generation** — explicit `max_tokens=1024` | Always on | **Cap.** Bounds worst-case cost/latency and reduces mid-JSON truncation (which would otherwise trip the validation gate). |

Not added as a guardrail: an action-count cap per turn. It would be defensive coding against a failure that has never been observed here, contrary to the project's stated conventions. Scope creep is instead *observed* as an offline signal (below), and promoted to a guardrail only if the signal actually fires.

### Offline (Flywheel)

At single-user volume the "flywheel" is a periodic 10-minute review, not a pipeline. All source data already exists in `chat_messages` and the app log.

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| **Malformed-output rate** (`outcome=malformed` warnings ÷ total turns) | Count from logs after any real usage session | If non-trivial (say, more than ~1 in 20 turns), Section 3's Pitfall #1/#2 have materialized: verify the schema reaches the wire (log `response._hidden_params`), then fall back to Section 2's recorded alternative — raw `httpx` POST with schema enforced via prompt + Pydantic validation. |
| **Timeout rate** (`outcome=timeout` ÷ total turns) | Same log scan | Already at `reasoning_effort="low"`; next levers are trimming `max_tokens` or the 20-message history window (CHAT-02). |
| **Action-report fidelity spot-check** (EV-1b, prose vs. reality) | `SELECT content, actions FROM chat_messages WHERE role='assistant' AND actions LIKE '%false%'` — turns containing a rejection are exactly where misreporting would surface | Any transcript that narrates a rejected action as successful is a prompt-engineering fix (strengthen the system-prompt instruction to report outcomes as given) — the structural guardrail already protects the payload, so this affects prose only. |
| **Context-grounding spot-check** (EV-4b) | 5 random assistant turns per review session, checked against the logged per-turn context | Fabricated figures indicate the portfolio context block needs to be more explicit/compact in the prompt. |
| **Scope-creep signal** | Turns where the executed action count exceeds 3, or where a ticker appears in `actions` but not in the user's message | If recurring, tighten the system prompt first; only then consider an enforced cap. |
| **Latency distribution** | `duration_ms` from the per-turn log line | Rising p95 approaching 30s means the timeout will start firing for real users; act before it does. |

## 7. Production Monitoring

**Honest framing:** there is no production. FinAlly is a single-container Docker app run locally by one person with simulated money (Section 1b: stakes *low*, population *one*). There is no ops team, no on-call, no alerting infrastructure, and no traffic to sample. Prescribing APM, a tracing platform, or paging thresholds here would be infrastructure this project does not have and does not need. What follows is deliberately the lightweight version, built on the logging convention already used across `app/market/`.

**Tracing tool:** stdlib `logging` with the established module-level pattern (`logger = logging.getLogger(__name__)` in `app/llm/`). Persistent trace storage is the existing `chat_messages` table. No external tool. *(If FinAlly ever gains real users or multi-user support, revisit — local Arize Phoenix is the pre-vetted upgrade path from Section 5.)*

**Key metrics to track** — one structured `INFO` line per chat turn, emitted by the router after the turn resolves:

```python
logger.info(
    "chat turn outcome=%s duration_ms=%d mock=%s trades=%d rejected=%d watchlist=%d",
    outcome, duration_ms, mock, n_trades, n_rejected, n_watchlist,
)
```

| Metric | Why it earns its place |
|--------|------------------------|
| `outcome` (`ok` / `timeout` / `malformed`) | The single most decision-driving field — directly feeds the two top flywheel metrics and tells you whether `gpt-oss-120b`'s documented `response_format` unreliability is biting in practice. |
| `duration_ms` | Early warning that the 30s timeout is about to start firing. |
| `n_trades` / `n_rejected` | Rejections are the highest-signal turns for the EV-1 fidelity spot-check; this makes them greppable without a SQL query. |
| `mock` | Guards against silently running the demo (or a "live" test) against the mock matcher. |

Do **not** log full prompts or raw responses at `info` — Section 4b already fixes this: raw output is logged only at `warning`, truncated, on the malformed path.

**Review triggers** (the honest analogue of alert thresholds — nothing pages anyone; these are "go look" conditions for the developer):

| Condition | Response |
|-----------|----------|
| Any `outcome=malformed` in a live session | Inspect the truncated raw output in the warning log; if repeated, execute the Section 2 fallback plan. |
| Any `outcome=timeout` in a live session | Check `duration_ms` on surrounding turns; confirm `reasoning_effort="low"` and `max_tokens` are actually applied. |
| Any turn with `rejected>0` | Read that transcript against its `actions` JSON — the EV-1b fidelity check. |
| `ERROR`-level entries from `app/llm/` | Should be empty by design: timeouts and malformed output are *expected, handled* conditions logged at `warning` (Section 4b). Anything at `error` is a genuine defect. |

Recipe: `docker logs finally 2>&1 | grep "chat turn"`.

**Smart sampling strategy:** with one user and a handful of turns per session, sampling is unnecessary — the population *is* the sample. Review 100% of flagged turns using the signal filters rather than a random subset:

```sql
-- Turns where misreporting would surface (any rejected action)
SELECT created_at, content, actions FROM chat_messages
WHERE role = 'assistant' AND actions LIKE '%"success": false%'
ORDER BY created_at DESC LIMIT 20;

-- Turns the user retried immediately (a dissatisfaction signal, per ai-evals.md
-- signal-metric divergence): two user messages with no assistant turn between them
SELECT created_at, content FROM chat_messages WHERE role = 'user' ORDER BY created_at;
```

Phase-completion gate: before marking Phase 3 done, the project owner (and, per Section 1b's expert-roles table, the course instructor / capstone reviewer if available) reads a sample of real non-mock transcripts against their `actions` JSON to calibrate what EV-1b and EV-4b mean in practice. That human read is the calibration step this project uses in place of a calibrated LLM judge.
