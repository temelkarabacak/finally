## Spacing Scale

Declared values (multiples of 4, matching Tailwind's default scale already in use):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | `py-1` button vertical padding, icon/glyph gaps |
| sm | 8px | `gap-2`, `px-2` — compact element spacing, input padding |
| md | 12px — **locked exception, not on the standard 4/8/16/24/32/48/64 scale** | `p-3` panel padding (WatchlistPanel, PriceChart — already shipped Phase 1) and submit-button `px-3 py-1` padding (Add, and now Buy/Sell). Locked because it must exactly match already-shipped, human-verified Phase 1 CSS; changing it now would visually regress `WatchlistPanel`/`PriceChart` outside this phase's scope. This is a deliberate, permanent extension of the 8-point scale for this one established value, not an oversight — no other non-standard value is permitted. |
| lg | 16px | `gap-4` — layout gaps between grid panels, `p-6` page padding uses 24px (below) |
| xl | 24px | `p-6` page-level padding (`main` in `page.tsx`) |
| 2xl | 48px | Reserved, no current usage |
| 3xl | 64px | Reserved, no current usage |

Exceptions: Buy/Sell and Add-style submit buttons use `px-3 py-1` (12px × 4px, the `md` locked exception above) — a ~28px-tall hit target, below the 44px touch-target guideline. This is a deliberate carry-forward of Phase 1's `WatchlistPanel` Add-button precedent for a desktop-first, data-dense terminal UI (per `planning/PLAN.md` §10, "Responsive but desktop-first"). No new touch-target exception is introduced beyond this existing one.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 (regular) | 1.5 |
| Label | 12px (`text-xs`) | 400 (regular) | 1.4 |
| Heading (panel title) | 14px (`text-sm`) | 600 (semibold), `uppercase tracking-wide` | 1.2 |
| Display (page title) | 20px (`text-xl`) | 600 (semibold) | 1.2 |

**Weights:** exactly two content weights — regular (400) and semibold (600) — matching Phase 1. Medium (500, `font-medium`) is **not** a third content weight; it is reserved exclusively for submit-button labels (Add/Buy/Sell), carried forward unchanged from `WatchlistPanel`'s Add button. Do not introduce a fourth weight.

**Numeric formatting:** all monetary and price values render via `font-mono` with `.toFixed(2)` (matching `WatchlistPanel`'s `tick.price.toFixed(2)`), so prices, cash, and P&L always show exactly 2 decimal places and align in a fixed-width column — a locked convention, not a per-component choice.

## Layout & Composition

*(Claude's discretion per 02-CONTEXT.md — resolved here so plan/executor have one concrete answer, not an open question.)*

**Trade Bar placement (UI-07):** A persistent, full-width horizontal strip directly below the header/connection row and above the two-column watchlist/chart grid — always visible regardless of which ticker is selected, since D-07 requires any selection (watchlist, positions, heatmap) to prefill it instantly. Fields left-to-right: Ticker text input (uppercase-normalized, same input style as the watchlist Add field), Quantity number input (accepts fractional values, `step="any"`, `min` just above 0), Buy button (purple), Sell button (purple). No confirmation dialog on either button (established zero-stakes design).

**Row layout below the trade bar:**
1. Existing two-column grid unchanged: Watchlist (≤420px) | Main price chart (fills remainder).
2. New row: Positions Table (left column, same ≤420px width as Watchlist, for visual column alignment) | Portfolio Heatmap (right column, fills remainder).
3. P&L Chart: full-width row beneath, spanning both columns.

**Header (UI-09):** Extends the existing header (`page.tsx:24-32`) without restructuring it. Left side unchanged (brand title). Right side becomes a stat cluster, left-to-right: Total Value → Cash Balance → Connection indicator, each `font-mono`, separated by a thin `border-l border-terminal-border` divider with `px-3` padding. The connection indicator becomes an actual dot (small `rounded-full` span, 8px, background color driven by status) plus its existing text label — not text alone — to satisfy PLAN.md §2's literal "small colored dot" requirement (green=connected, yellow=reconnecting, red=disconnected).

**Header value flash (Claude's discretion):** Total Value and Cash Balance do **not** flash on change, unlike watchlist prices. PLAN.md §2 only specifies the flash animation for watchlist price cells; applying it to two header numbers that can update ~2×/second from live price streaming would read as a persistent strobe at the top of the screen. Header values update silently; only the underlying watchlist rows flash.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Trade bar has two: **Buy** and **Sell** — verb-only labels, no "Buy Shares" / "Place Order" wording |
| Empty state heading (Positions Table, D-01) | "No positions yet" |
| Empty state body (Positions Table, D-01) | "Buy shares to get started." |
| Empty state heading (Heatmap, D-02) | "No positions yet" (identical to Positions Table, per D-02's "same empty-state message pattern") |
| Empty state body (Heatmap, D-02) | "Buy shares to get started." |
| Empty state heading (P&L Chart, D-03) | "Building portfolio history" |
| Empty state body (P&L Chart, D-03) | "Chart appears once enough data points are recorded — usually within a minute." (distinct from the positions/heatmap wording: this state is never resolved by trading, only by the always-on 30s snapshot recorder per D-04) |
| Error state — insufficient cash | "Not enough cash to buy {quantity} {ticker} — try a smaller quantity." |
| Error state — insufficient shares | "You only hold {heldQty} shares of {ticker} — try a smaller quantity." |
| Error state — no live price | "No live price for {ticker} yet — add it to your watchlist first." |
| Error state — generic trade failure | "Could not complete that trade — try again." |
| Destructive confirmation | **None.** Per `planning/PLAN.md` §2/§9 explicit design choice, trades and watchlist removal execute instantly with zero confirmation dialogs anywhere in this phase (simulated money, zero stakes) — there is no destructive-action copy to write. |

Copy is terse, terminal-appropriate (lowercase-first sentence fragments, no exclamation points), matching Phase 1's `errorMessage` tone (e.g. "{ticker} is already on the watchlist"). Exact wording remains open to minor refinement during implementation per 02-CONTEXT.md, provided it keeps this tone and states the reason + next step.

**Resolved exception — "Buy"/"Sell" single-word CTAs:** These labels are single words without a noun, which technically triggers the copywriting FLAG criterion ("single word without a noun"). This is a deliberate, resolved exception, not an oversight: the verb reads unambiguously because it sits directly beside the always-visible Ticker and Quantity fields in the trade bar (per the Layout & Composition section above), so the noun is supplied by the adjacent form context rather than by the button label itself. "Buy Shares" / "Sell Shares" was considered and rejected as redundant given that context.

| loading | Positions Table (list-collection) | ✅ covered | Before the first `GET /api/portfolio` response resolves, shows the same empty-state message as true-empty (no separate skeleton) — acceptable since the fetch is same-origin and typically resolves in well under a second |

| overflow | Positions Table (list-collection) | 🧪 backstop | Beyond ~8-10 rows the panel scrolls internally (`overflow-y-auto` with a bounded `max-height`) rather than pushing page layout — visual-only, needs a manual/visual check, not a unit-testable assertion |
| zero-one-many | Positions Table (list-collection) | ✅ covered | Zero = empty state (D-01); one or many = identical row rendering, no singular/plural copy needed (numeric/symbolic content, not prose) |
| empty | Portfolio Heatmap (list-collection) | ✅ covered | D-02: identical empty-state message pattern in place of the treemap |
| populated | Portfolio Heatmap (list-collection) | ✅ covered | Recharts `Treemap`, cells sized by position weight (value / total value), colored via `--color-up`/`--color-down` by P&L sign, ticker label per cell, tile click drives shared `selectedTicker` (D-06) with blue highlight (D-08, clarified above) |
| overflow | Portfolio Heatmap (list-collection) | 🧪 backstop | Cells below a minimum readable size (<24px in either dimension) suppress the ticker text label rather than clipping/overlapping it — visual-only |
| zero-one-many | Portfolio Heatmap (list-collection) | ✅ covered | One position renders as a single full-panel cell (native Recharts `Treemap` behavior) |
| empty | P&L Chart (media) | ✅ covered | D-03: empty-state message pattern until ≥2 snapshot points exist |
| loading | P&L Chart (media) | ✅ covered | Before the first `GET /api/portfolio/history` response, shows the same empty-state treatment as <2 points (no separate skeleton) |
| error | P&L Chart (media) | ✅ covered | History fetch failure shows inline error text in the panel header area, reusing the established `text-down` pattern, rather than silently rendering an empty chart |
| populated | P&L Chart (media) | ✅ covered | `lightweight-charts` line series mirrors `PriceChart.tsx` exactly (same grid/axis/color tokens), x=time, y=total portfolio value |
| empty/partial | Trade Bar (form) | ✅ covered | Buy/Sell buttons are disabled (not silently no-op) until both a valid ticker and quantity > 0 are present — an incomplete form cannot submit a malformed request |
| loading | Trade Bar (form) | ✅ covered | While `POST /api/portfolio/trade` is in flight, Buy/Sell show a disabled/pending state (reduced opacity + label swap, e.g. "Submitting…") to prevent duplicate double-click submissions given there is no confirmation dialog |
| error | Trade Bar (form) | ✅ covered | Server rejection shows inline error text below the bar (see Copywriting Contract); fields are NOT cleared, so the user can adjust and resubmit |
| loading | Header stats (static-content) | ✅ covered | Total Value / Cash show `"--"` (mirrors `WatchlistPanel`'s `tick ? tick.price.toFixed(2) : "--"`) before the first `/api/portfolio` response — never `$0.00`, which would misrepresent an unloaded state as an actual zero balance |
| error | Header stats (static-content) | 🧪 backstop | On a portfolio-fetch failure, Total Value/Cash freeze at their last-known values rather than reverting to `"--"` (the connection-status dot communicates degradation separately) — needs an explicit held-out test asserting stale-value retention, not a visual-only check |
