# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — plain HTML + Tailwind v4 utility classes, same as Phases 1–2 |
| Icon library | none — Unicode glyphs / text labels only (`aria-label`-annotated buttons, no icon package installed), consistent with `WatchlistPanel.tsx`'s remove control |
| Font | `ui-monospace, "SFMono-Regular", Menlo, Consolas, "Liberation Mono", monospace` via the `--font-mono` token, applied globally on `<body>` — one font for the whole app including chat prose, no secondary display font introduced this phase |

**shadcn gate note:** `components.json` is absent and this is a React/Next.js project, which would normally trigger the shadcn-init prompt. Not re-triggered here, for the same reason recorded in `02-UI-SPEC.md`: Phase 1 established and human-verified a complete hand-rolled Tailwind v4 `@theme` token system (`frontend/app/globals.css`) as a **locked decision** (`.planning/PROJECT.md` Key Decisions). Phase 2 extended it without introducing a component library, and the chat drawer/message list/confirmation cards in this phase are simple enough (bordered boxes, flex layout, text) that reaching for a component library would fork the design system two phases in, not simplify anything. This phase extends the existing token system only.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 (regular) | 1.5 |
| Label | 12px (`text-xs`) | 400 (regular) | 1.4 |
| Heading (panel title) | 14px (`text-sm`) | 600 (semibold), `uppercase tracking-wide` | 1.2 |
| Display (page title) | 20px (`text-xl`) | 600 (semibold) | 1.2 — unchanged, not used by this phase's new components |

**Weights:** exactly two content weights — regular (400) and semibold (600) — unchanged from Phase 1/2. Medium (500, `font-medium`) remains reserved exclusively for submit-style button labels (Add/Buy/Sell, and now Send and the quick-prompt buttons — see Color below for why quick-prompts count as "submit"). No new weight introduced.

**Numeric formatting:** trade confirmation card figures (fill price, quantity) render via `font-mono` using the shared `frontend/lib/format.ts` `formatCurrency` helper for prices and `.toFixed(2)`-equivalent fixed precision for quantities where fractional, matching the locked Phase 1/2 convention — no new formatting rule for this phase.

**Chat-specific type usage:**
- Message bubble text (user + assistant): Body (14px/400/1.5) — conversational prose needs the more readable line-height, not the tighter Label spacing.
- Message timestamp (if shown): Label (12px/400) — matches Phase 1/2's use of `text-xs` for secondary/meta text.
- "AI Chat" drawer panel title: Heading role (14px/600, uppercase tracking-wide), identical treatment to "Watchlist"/"Positions"/"Heatmap"/"P&L" panel titles.
- Trade confirmation card ticker/side (e.g. "BUY AAPL"): Body weight but `font-semibold` for the ticker only, mirroring how Positions Table already bolds ticker symbols — not a third weight, this is the existing semibold role applied to a new element.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0d1117` (`--color-terminal-bg`) | App background; also the chat drawer's own container surface (see Layout — the drawer nests panels the same way the page nests panels) |
| Secondary (30%) | `#1a1a2e` (`--color-terminal-panel`) | Message bubbles (both user and assistant), trade/watchlist confirmation cards, quick-prompt buttons' resting surface |
| Accent (10%) | `#ecad0a` (`--color-accent-yellow`) | Reserved for: brand/page title ("FinAlly", unchanged), all panel-section title labels including the new "AI Chat" drawer header — no new reservation, same rule as Phase 1/2 |
| Destructive | `#f85149` (`--color-down`, reused — no new token) | Reserved for: rejected-trade confirmation card border + "REJECTED" label (D-05), the timeout/error bubble's left border (D-09), and existing Trade Bar error text — one semantic red across the app, not a phase-specific color |

**Additional locked semantic pair (unchanged from Phase 1/2, extended to this phase's new elements):**

| Token | Value | Usage |
|-------|-------|-------|
| `--color-up` | `#3fb950` | Successful trade confirmation card's left border (D-04) — extends the existing "green = positive/successful outcome" semantic already used for uptick flashes and positive P&L; no new token |
| `--color-down` | `#f85149` | Rejected trade confirmation card's left border + "REJECTED" label (D-05); timeout/malformed-output error bubble's left border (D-09) |
| `--color-accent-blue` (`#209dd7`) | Unchanged role (selected-row/tile highlight, chart line color) — **not** used for chat message differentiation; see rationale below |
| `--color-accent-purple` (`#753991`) | **All** submit-style buttons, extended this phase to: the chat **Send** button and the **quick-prompt buttons** (D-08 makes a quick-prompt click behave exactly like submitting that text — same zero-friction, instant-send semantics as Buy/Sell/Add), alongside the existing Buy/Sell/Add |

**Message bubble differentiation — resolved (Claude's discretion, flagged open in 03-CONTEXT.md/03-RESEARCH.md):** User and assistant bubbles use **identical** surface color (`terminal-panel`) and border (`terminal-border`); the only differentiator is horizontal alignment — user messages right-aligned, assistant messages left-aligned. This is a deliberate, minimal choice: introducing a third role for `accent-blue` (beyond its existing "selection highlight" + "chart line" duties) would blur what that color communicates elsewhere in the app, and the project's "do not overengineer" convention favors the simplest signal (alignment) that already reads clearly in every chat UI pattern. Do not add a colored border/background to differentiate sender — alignment alone is the contract.

**Toggle button color — resolved:** The floating chat toggle ("AI Chat" / "Close Chat") is a navigation control, not a submit action — it does **not** use `accent-purple`. It uses the same bordered/neutral treatment as any secondary chrome element: `bg-terminal-panel border border-terminal-border text-terminal-text`, matching e.g. the remove-ticker control's neutral resting state before hover. Reserving purple strictly for "this click causes a trade/watchlist/chat-send action" keeps the color's meaning consistent.

Accent reserved for: brand title, panel section-title labels (including "AI Chat") only — never buttons, never selection state, never data values, never message-sender differentiation. Unchanged from Phase 1/2, explicitly re-confirmed for this phase's new surfaces.

## Layout & Composition

*(Claude's discretion informed by 03-CONTEXT.md D-01/D-02/D-03 and 03-RESEARCH.md Pattern 3 — resolved here as one concrete answer.)*

**Toggle control:** A fixed-position pill button, `fixed bottom-4 right-4 z-50`, always visible regardless of scroll position, label "AI Chat" when closed / "Close Chat" when open (D-03: closed by default on first load). Neutral bordered styling per Color above — this is the one persistent hint that the AI feature exists without it competing visually with the live-price grid.

**Drawer (D-01/D-02):** `fixed inset-x-0 bottom-0 z-40` (below the toggle's `z-50` so the toggle stays visibly stacked above it while open), fixed height `h-96` (384px — a multiple of 4, consistent with the existing `h-72`/`h-64` panel-height precedent from Phase 2, not a new arbitrary value), `border-t border-terminal-border`, `bg-terminal-bg` surface (matches the page's own dominant-color role — the drawer is a self-contained mini-page, not a card). It **overlays** the grid beneath it (D-02) — no reflow of `WatchlistPanel`/`PriceChart`/`PositionsTable`/`PortfolioHeatmap`/`PnlChart`, accepted tradeoff per the locked decision that it can obscure content while open.

**Internal drawer structure, top to bottom:**
1. Header row (`h-auto`, `p-3`, `border-b border-terminal-border`): "AI Chat" panel title (Heading role, accent-yellow, uppercase tracking-wide) — no separate close button needed here since the floating toggle already handles close.
2. Message list (`flex-1 overflow-y-auto p-4`, `gap-2` between bubbles): scrolls internally, newest message at the bottom, auto-scrolls to bottom on new message arrival (mirrors how a chat transcript is expected to behave — not explicitly decided in CONTEXT.md but the only sensible default). When empty (D-07), replaced by the quick-prompt block (see below) instead of an empty scroll area.
3. Input row (`border-t border-terminal-border p-3`, `flex items-center gap-2`, pinned to drawer bottom): text input (`flex-1`, same bordered/mono styling as `TradeBar`'s ticker/quantity inputs) + Send button (`accent-purple`, matches Buy/Sell/Add styling exactly). Disabled while a request is in flight, mirroring `TradeBar`'s `submitting` pattern exactly (D-08's "no confirmation dialog" philosophy extends to "no double-send," same as trades).

**Quick-prompt block (D-07/D-08):** Renders in place of the message list's content only when the conversation is empty (zero messages after history load resolves) — three buttons, `flex flex-wrap gap-2`, same `accent-purple` submit styling as Send, each click immediately calls the same send path as typing + pressing Send (D-08) — never just populates the input box. Disappears permanently for that session once the first message exists; does not reappear after that turn even if a later error clears the transcript view (it never does — see Copywriting error contract).

**Trade confirmation card (D-04/D-05):** A distinct block rendered inline within the assistant's turn, visually separated from the message bubble (not nested inside its text) — `border-l-4` (thicker than the drawer's 1px borders elsewhere, so it reads as a distinct object per D-04's "not just a sentence"), `bg-terminal-panel`, `p-3`, `rounded`, `font-mono` for the numeric fields. One card per executed trade (D-04 lists one summary card per trade, so a multi-trade turn renders one card per trade, stacked with `gap-2`, not merged into a single card).
- Success: `border-l-up`, content shape `{SIDE} {quantity} {ticker} @ {fill_price}` (e.g. "BUY 10 AAPL @ $190.24"), ticker `font-semibold`.
- Rejected (D-05, same component, failed variant): `border-l-down`, an uppercase `text-down text-xs font-semibold` "REJECTED" label above the attempted action line, plus the rejection reason text below in Body role.

**Watchlist change reporting (D-06):** No card, no distinct component — rendered as plain prose inside the assistant's message bubble (the LLM's own `message` text narrates it), identical styling to any other assistant bubble content. This is intentionally the simplest possible treatment, matching D-06's "lower-stakes, no money moves" rationale.

**Timeout/error bubble (D-09/D-10):** Same component and shape as a normal assistant message bubble — left-aligned, `bg-terminal-panel` — with one visual difference: `border-down` (instead of the default `border-terminal-border`) on the bubble itself, no separate icon or "ERROR" label (the copy alone communicates it; see Copywriting Contract). The user's original message text is **not** cleared from the input box (D-10) — the send handler must fail without touching the input's own state.

**Chat history on drawer open:** History fetch (last N persisted `chat_messages`) happens once, on the drawer's first open per page session — not eagerly on page load, consistent with D-03's "collapsed by default, chat is opt-in" philosophy, and avoiding an unnecessary request for a user who never opens chat. While that fetch is pending, the message-list area shows a brief `text-terminal-muted text-sm` "Loading conversation…" line in place of both the quick-prompt block and any messages, resolving to one of: populated history, or (if genuinely empty) the quick-prompt block. **Flag for planner:** this requires a `GET` endpoint to serve persisted history, which is not yet named in `03-RESEARCH.md`'s router surface (only `POST /api/chat` is scoped there) — the planner should confirm/add this endpoint; this UI-SPEC only fixes the client-side fetch-on-first-open behavior and its three-state (loading/empty/populated) treatment.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (chat send) | **Send** — single-word CTA, same resolved exception as Buy/Sell (adjacent input field supplies the noun) |
| Toggle control | "AI Chat" (closed state) / "Close Chat" (open state) — exact pair, locked |
| Chat input placeholder | "Ask FinAlly..." — echoes the assistant's own name (PLAN.md §9: "FinAlly, an AI trading assistant"), terse, no exclamation |
| Quick-prompt buttons (D-07, exactly 3) | "Analyze my portfolio" · "What should I buy?" · "Add a ticker to watchlist" — terse, terminal-appropriate, matches Phase 2's established tone; exact wording is a locked default but may be refined during implementation provided it stays terse and covers one analysis prompt + one advice prompt + one action prompt |
| Empty state heading (chat, first open) | none — quick-prompt buttons themselves are the empty-state treatment, no separate heading copy needed above them |
| Empty state body (chat, first open) | "Ask about your portfolio, or tell me what to trade." — sits above the quick-prompt buttons as brief framing text |
| Loading state (history fetch) | "Loading conversation…" |
| Loading state (awaiting LLM reply) | "Thinking…" shown as a lightweight inline indicator (not a full bubble) at the bottom of the message list while a request is in flight — mirrors `TradeBar`'s "Submitting…" label-swap pattern rather than inventing a new loading idiom |
| Generic retry message (CHAT-05 timeout + EV-2 malformed-output — **one shared string, both paths**) | "Something went wrong — please try again." — must exactly match the backend's `GENERIC_RETRY_MESSAGE` constant (per `03-AI-SPEC.md` §6/EV-6: the frontend renders this string verbatim inside the error-bordered bubble described above, it does not compose or reword it client-side) |
| Trade confirmation — success | "{SIDE} {quantity} {ticker} @ {fill_price}" (e.g. "BUY 10 AAPL @ $190.24") — SIDE uppercase, matches the card structure in Layout |
| Trade confirmation — rejected | Label: "REJECTED" (uppercase, `text-down`). Body: "{SIDE} {quantity} {ticker}: {reason}" where `{reason}` is the same rejection text `execute_trade()` already returns for the manual Trade Bar (e.g. "Not enough cash..." / "You only hold..."), reused verbatim — not a new error vocabulary for the LLM path |
| Watchlist change (D-06) | No fixed template — LLM-generated prose inside the assistant's `message` field (system-prompt-guided, per AI-SPEC §4b), rendered as-is |
| Destructive confirmation | **None.** Same project-wide, twice-already-locked decision (Phase 1/2): trades and watchlist changes — whether manual or AI-executed — fire instantly with zero confirmation dialogs. There is no destructive-action copy to write for this phase either. |

Copy stays terse, terminal-appropriate (lowercase-first sentence fragments where not a proper noun, no exclamation points), matching Phase 1/2's established tone throughout.

| Category | Element(s) | Status | Resolution / Reason |

| loading | Chat message list — awaiting LLM reply (list-collection) | ✅ covered | "Thinking…" inline indicator at the list's bottom; Send button disabled during the request, mirroring `TradeBar`'s `submitting` pattern |

| error | Chat message list — network/transport failure (not timeout) (list-collection) | 🧪 backstop | Not explicitly scoped in CONTEXT.md (only the 30s LLM timeout is named). | overflow | Chat message list (list-collection) | ✅ covered | `overflow-y-auto` on the message list container, fixed drawer height — long conversations scroll internally, never grow the drawer or push page content |
| overflow | Chat message bubble text (static-content, long-text) | ✅ covered | Bubble `max-width` (~80% of drawer width) with natural text wrapping (`whitespace-pre-wrap` for user-typed newlines) — no truncation, no ellipsis |
| overflow | Chat input field (form, long-text) | 🧪 backstop | A long pasted message should not force the drawer to grow — input should scroll/wrap within a bounded height (e.g. `max-h-24` with internal scroll) rather than pushing the Send button off-screen; visual-only, needs a manual check |
| zero-one-many | Trade confirmation cards per turn (list-collection) | ✅ covered | Zero trades = no cards, only the message bubble; one or many = one stacked card per trade, per Layout |
| zero-one-many | Quick-prompt buttons | ✅ covered | Exactly 3, fixed set (not dynamic/variable-length) — no zero/many case to handle |
| empty | Rejected-trade reason text (static-content) | ✅ covered | Every rejected card always carries a `{reason}` string reused from `execute_trade()`'s existing rejection copy — there is no rejection path that produces an empty reason, so no fallback copy is needed |
| long-text | Trade confirmation card reason text (static-content) | ⚠ unresolved | If a future rejection reason string grows longer than the card's fixed width (none currently do, per the existing Trade Bar reasons), wrapping behavior is undefined — deferred as a planner assumption since no current reason string is long enough to trigger it |
| populated | Toggle control state (static-content) | ✅ covered | Label swaps "AI Chat" ↔ "Close Chat" synchronously with open/closed state, no loading state needed (pure client-side boolean toggle) |
| loading | Send button (form) | ✅ covered | Disabled + `"Sending…"` label swap while in flight, mirrors `TradeBar`'s "Submitting…" convention exactly — prevents a double-send given there's no confirmation dialog |

|----------|-------------|--------------|
