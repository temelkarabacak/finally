<objective>
Give the whole app a one-command lifecycle on both macOS/Linux and Windows: `start_mac.sh` / `start_windows.ps1` build the image if needed and run the container with the `db/` bind mount, `stop_mac.sh` / `stop_windows.ps1` stop it within a bounded window. All four are safe to run repeatedly, and stopping never touches the user's data.

Purpose: DEPLOY-03 — the "single command" half of the phase goal. These scripts are the only interface most users will ever touch, so they must be forgiving (already-running, already-stopped, Docker not running, no `.env`) rather than throwing raw Docker CLI errors.

Output: `scripts/start_mac.sh`, `scripts/stop_mac.sh`, `scripts/start_windows.ps1`, `scripts/stop_windows.ps1`.
</objective>

Shared constants: image tag `finally`, container name `finally-app`, host port `8000`.

`scripts/start_mac.sh`:

Preflight — run `docker info` redirected to /dev/null; if it exits non-zero, print a plain-language message telling the user Docker is not running and to start Docker Desktop (or the Docker daemon), then exit 1. Do not let a raw Docker CLI error be the user's first experience.

Build gate — build with `docker build -t finally "$REPO_ROOT"` when either `docker image inspect finally` fails (no image yet) or the first argument is `--build` (explicit rebuild). Otherwise skip the build so a repeat run is fast.

Env gate — assemble the run arguments so `--env-file "$REPO_ROOT/.env"` is included only when that file exists. When it is absent, print a one-line notice that AI chat will be unavailable without `OPENROUTER_API_KEY` and start anyway: per 04-CONTEXT.md's startup-experience discretion, prices and trading work fine without an LLM key, so a missing key must never block startup.

Lifecycle branch — read `docker inspect -f '{{.State.Running}}' finally-app` with stderr suppressed, defaulting to the literal `absent` when that command fails. Branch on three states: `true` prints that the app is already running at http://localhost:8000 and exits 0 (this is the idempotency case, not an error); `false` runs `docker start finally-app`; `absent` runs `docker run -d --name finally-app -v "$REPO_ROOT/db:/app/db" -p 8000:8000 --stop-timeout 15 "$IMAGE"` plus the optional env-file argument. Create `$REPO_ROOT/db` with `mkdir -p` before the run so the bind-mount source always exists.

The bind mount is `"$REPO_ROOT/db":/app/db` per decision D-01 — a host directory, never a named Docker volume — so the user can inspect, back up, or delete `db/finally.db` directly. `--stop-timeout 15` is deliberately larger than the image's `--timeout-graceful-shutdown 10` so uvicorn's own bounded cancellation resolves first and Docker's SIGKILL stays a last resort.

Readiness — after starting, poll `http://localhost:8000/api/health` with the same 40 x 0.5s loop from `smoke.sh`, then print `Open http://localhost:8000`. If the poll times out, print the last 20 lines of `docker logs finally-app` and exit 1 rather than pointing the user at a URL that will not answer. Opening the browser is best-effort and optional per planning/PLAN.md §11: if the `open` command exists, invoke it on the URL suppressing any error; never fail the script because a browser could not be launched.

`scripts/stop_mac.sh`:

Run the same `docker info` preflight. Then read the same `docker inspect -f '{{.State.Running}}'` state. When running, issue `docker stop --timeout 15 finally-app` and print a confirmation that data in `db/` is preserved. When the container exists but is stopped, or does not exist at all, print that the app is not running and exit 0 — never a non-zero exit, because running stop twice must be safe.

The stop script issues a bounded container-stop and nothing else. It must never issue a container-remove or a volume-remove subcommand, and must never delete anything under `db/`: DEPLOY-03 requires that stopping preserve the user's portfolio, and a removal here would destroy exactly the state this phase exists to protect. Do not reuse `smoke.sh`'s cleanup trap shape here — its unbounded `kill` then `wait` is the reproduction of the shutdown hang, not the fix.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host `.env` → container process env | The scripts are the only place secrets cross into the container, and only via `--env-file` at run time |
| host `db/` directory → container `/app/db` | The durable user data path; a script that removes the container or the directory destroys it |
| host shell → Docker daemon | Scripts must tolerate an unavailable daemon without leaking a confusing CLI error |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-07 | Denial of Service (data loss) | `scripts/stop_mac.sh`, `scripts/stop_windows.ps1` | high | mitigate | Stop scripts issue a bounded container-stop only; verified by a filtered negative grep for container-remove and volume-remove subcommands, plus asserting `db/finally.db` persists after two stop runs |
| T-04-01 | Information Disclosure | `--env-file` handling in the start scripts | high | mitigate | Secrets are passed by file reference at run time only; the scripts never echo the file contents and never pass secret values as `-e KEY=value` arguments visible in `docker inspect` or the process table |
| T-04-03 | Denial of Service (self-inflicted) | bounded stop | medium | mitigate | `--stop-timeout 15` at run time and `--timeout 15` on stop, both larger than the image's 10s uvicorn graceful-shutdown window |
| T-04-04 | Elevation of Privilege | container default user (root) | low | accept | Single-user localhost deployment; a fixed non-root UID breaks writes to a bind mount owned by an arbitrary host user (04-RESEARCH.md Open Question 2) |
</threat_model>
